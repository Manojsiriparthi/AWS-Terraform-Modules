# 🗄️ Module: RDS (Relational Database Service)

> **Spoon-feeding guide — every single line explained.**

## 📦 What Does This Module Create?

| Resource | What it is |
|----------|-----------|
| `aws_db_subnet_group` | Tells RDS which subnets it can use |
| `aws_db_parameter_group` | MySQL tuning settings |
| `aws_db_instance.primary` | The main read-write MySQL database |
| `aws_db_instance.replica` (×N) | Read-only replicas (using `count`) |

## 🔍 What is RDS?

RDS = Relational Database Service. It is a **managed MySQL** (or Postgres, etc.) database.

```
WITHOUT RDS (self-managed on EC2):
  You install MySQL on an EC2 instance.
  You manage backups manually.
  You handle patching MySQL yourself.
  Instance fails? You restore manually from backup.
  Hours of downtime.

WITH RDS:
  AWS manages: patching, backups, failover.
  Automated backups every day, kept for 7 days.
  Multi-AZ: if primary fails, standby promoted in ~60 seconds.
  You just connect and run queries.
```

**Password security in this module:**
The RDS password is NEVER stored in tfvars or code.
It is generated by the `secrets_manager` module and passed here as a
`sensitive` variable — Terraform never prints it in plan/apply output.

## 🔍 PART 1 — DB Subnet Group

```hcl
resource "aws_db_subnet_group" "main" {
  name       = "${var.environment}-db-subnet-group"
  subnet_ids = var.private_subnet_ids
  ...
}
```

**What is a DB subnet group?**
RDS needs to know which subnets it can place database instances in.

**Why private subnets?**
```
PUBLIC subnet:
  RDS instance gets a public IP.
  Anyone on the internet can try to connect on port 3306.
  Brute-force attacks. Possible data breach.
  NEVER do this.

PRIVATE subnet:
  RDS instance has only a private IP.
  Only resources inside the VPC can reach it.
  Security group further restricts to only the EC2 SG.
  Database is completely shielded from the internet.
```

**Why multiple subnets (2 AZs)?**
For Multi-AZ and read replicas, AWS needs subnets in at least 2 different
Availability Zones. The subnet group provides this list.

## 🔍 PART 2 — DB Parameter Group

```hcl
resource "aws_db_parameter_group" "main" {
  name   = "${var.environment}-mysql-params"
  family = "mysql8.0"

  parameter {
    name  = "slow_query_log"
    value = "1"
  }

  parameter {
    name  = "long_query_time"
    value = "2"
  }

  lifecycle {
    create_before_destroy = true
  }
}
```

**What is a parameter group?**
MySQL has hundreds of configuration settings (buffer sizes, timeouts, logging, etc.).
A parameter group is a named collection of these settings applied to an RDS instance.

**Without a parameter group:**
RDS uses the default parameter group, which you can't modify.

**`slow_query_log = "1"`**
- Enables logging of slow queries (queries that take longer than `long_query_time`).
- Stored in CloudWatch Logs.
- Invaluable for finding performance bottlenecks.

**`long_query_time = "2"`**
- Any query taking more than 2 seconds is logged as "slow."
- Check CloudWatch Logs → `/aws/rds/instance/dev-mysql-primary/slowquery` for these.

**`lifecycle { create_before_destroy = true }`**

```
The problem:
  You change a parameter (e.g., increase buffer size).
  Parameter groups CANNOT be updated in place — RDS creates a new one.
  Terraform tries to delete the old one FIRST.
  But the RDS instance still references the old group → deletion FAILS.

With create_before_destroy:
  New parameter group created first.
  RDS updated to use new group.
  Old group deleted. No error.
```

## 🔍 PART 3 — Primary RDS Instance

```hcl
resource "aws_db_instance" "primary" {
  identifier = "${var.environment}-mysql-primary"

  engine         = "mysql"
  engine_version = "8.0"
  instance_class = var.db_instance_class
  ...
}
```

**`identifier`** — unique name for this RDS instance in AWS.
The connection endpoint uses this: `dev-mysql-primary.xxxx.us-east-1.rds.amazonaws.com`

**`engine = "mysql"` and `engine_version = "8.0"`**
- Use MySQL 8.0 — current LTS version with JSON support, window functions, better performance.

**`instance_class = var.db_instance_class`**
- The hardware size: `db.t3.micro` (dev, free tier), `db.t3.medium` (prod).
- Larger class = more RAM (bigger buffer pool = faster queries).

### Storage

```hcl
  allocated_storage = var.db_storage_gb   # default 20GB
  storage_type      = "gp3"
  storage_encrypted = true
```

**`storage_type = "gp3"`** — General Purpose SSD v3. Best default for most workloads.
Better throughput than `gp2`, lower cost.

**`storage_encrypted = true`** — data on disk is encrypted.
Required for compliance (HIPAA, PCI-DSS). Always enable.

### Credentials

```hcl
  db_name  = var.db_name     # "appdb"
  username = var.db_username # "admin"
  password = var.db_password # comes from secrets_manager module — never plain text
```

**`db_name`** — initial database created inside MySQL. Your app connects to this.

**`password = var.db_password`** — the password is passed from the `secrets_manager`
module as a sensitive output. It never appears in:
- `terraform plan` output
- `terraform apply` output
- CI/CD logs
- Git history

### Networking

```hcl
  db_subnet_group_name   = aws_db_subnet_group.main.name
  vpc_security_group_ids = [var.rds_security_group_id]
  publicly_accessible    = false
```

**`db_subnet_group_name`** — places the instance in private subnets (defined above).

**`vpc_security_group_ids`** — attach the RDS security group (only port 3306 from EC2 SG).

**`publicly_accessible = false`** — NO public endpoint. Even if placed in a public
subnet (which we don't), no public DNS hostname would be created.

### Backups and Maintenance

```hcl
  backup_retention_period = var.backup_retention_days  # 7
  backup_window           = "03:00-04:00"
  maintenance_window      = "Mon:04:00-Mon:05:00"
```

**`backup_retention_period = 7`** — keep 7 days of automated daily snapshots.
Restore to any point-in-time within those 7 days if needed.

**`backup_window = "03:00-04:00"`** — backup runs at 3 AM UTC.
Choose the time with lowest traffic in your region.

**`maintenance_window`** — when AWS can apply minor patches/updates.
Set it to the quietest time in your week.

### Multi-AZ

```hcl
  multi_az = var.multi_az_enabled  # false in dev, true in prod
```

```
multi_az = false (dev):
  One DB instance. If AZ goes down, DB is unavailable.
  Acceptable in dev — costs less.

multi_az = true (prod):
  AWS creates a SYNCHRONOUS standby in a second AZ.
  Every write to primary is mirrored to standby before acknowledged.
  AZ failure: standby promoted automatically in ~60 seconds.
  No data loss. Minimal downtime.
```

### Lifecycle

```hcl
  lifecycle {
    prevent_destroy = false      # set true in prod
    ignore_changes  = [password]
  }
```

**`prevent_destroy = false`** — in prod, set `true` to block `terraform destroy`.

**`ignore_changes = [password]`**
```
The problem without this:
  Secrets Manager rotates the password (or you manually update the secret).
  RDS password on AWS doesn't change (app reconnects with new secret).
  Next `terraform plan`: Terraform detects password in state ≠ new value.
  Terraform wants to UPDATE the RDS password (triggering a maintenance event).
  Causes brief DB interruption during business hours.

With ignore_changes = [password]:
  Terraform stops tracking the password field after first creation.
  Secrets Manager can rotate freely. No interference.
```

**`depends_on = [var.secret_version_dependency]`**
```
The problem without this:
  Terraform starts creating the RDS instance.
  The Secrets Manager secret version hasn't been written yet.
  RDS gets created with an empty/wrong password.
  App can't connect. Data corruption risk.

With depends_on:
  Wait for the secret version to be fully written FIRST.
  Then create RDS using the now-available password.
```

## 🔍 PART 4 — Read Replicas

```hcl
resource "aws_db_instance" "replica" {
  count = var.replica_count   # dev=1, test/prod=2

  identifier          = "${var.environment}-mysql-replica-${count.index}"
  replicate_source_db = aws_db_instance.primary.identifier
  instance_class      = var.replica_instance_class
  ...
}
```

**What is a read replica?**

```
PRIMARY (read-write):
  Your app writes orders, user data, etc. here.

READ REPLICA (read-only):
  An exact copy of the primary, updated continuously.
  Your app reads reports, analytics, search queries from here.
  Takes load off the primary → primary stays fast for writes.
  2 replicas = 3x the read capacity.
```

**`count = var.replica_count`**
- dev: `1` replica (saves cost, proves the concept)
- test/prod: `2` replicas

**`replicate_source_db = aws_db_instance.primary.identifier`**
- Tells AWS: "this is a replica of the primary."
- AWS sets up continuous replication automatically.
- DO NOT specify `db_name`, `username`, `password` for replicas —
  they inherit these from the primary.

**`backup_retention_period = 0`** for replicas
- Replicas don't need their own backups — the primary's backups cover recovery.
- Enabling backups on replicas adds cost with no benefit in this setup.

**`depends_on = [aws_db_instance.primary]`**
- The primary must be FULLY ACTIVE before a replica can be created.
- `ACTIVE` state means the primary has finished its initial setup and is accepting connections.

**`lifecycle { ignore_changes = [replicate_source_db] }`**
- After creation, AWS manages the replication relationship internally.
- If Terraform tracks this field, minor AWS-side updates cause unwanted plan diffs.

## ⚡ Key Concepts Used

| Concept | Where | Why |
|---------|-------|-----|
| `count` | read replicas | Create N replicas from 1 resource block |
| `count.index` | replica naming | Each replica gets a unique name |
| `depends_on` | primary instance, replicas | Ordering: secret → primary → replicas |
| `lifecycle prevent_destroy` | primary (prod) | Block accidental delete |
| `lifecycle ignore_changes` | password, replicate_source | Don't fight Secrets Manager rotations |
| `lifecycle create_before_destroy` | parameter group | No orphaned group during update |
| `sensitive` variable | db_password | Never printed in plan/apply output |
