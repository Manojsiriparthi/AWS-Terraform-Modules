# 🔐 Module: Secrets Manager

> **Spoon-feeding guide — every single line explained.**
> This module solves one of the most common security mistakes in Terraform: hardcoded passwords.

---

## 📦 What Does This Module Create?

| Resource | What it is |
|----------|-----------|
| `random_password` | Auto-generates a cryptographically secure 24-char password |
| `aws_secretsmanager_secret` | The secret container (name + metadata) |
| `aws_secretsmanager_secret_version` | The actual secret value (stored as JSON) |
| `data aws_iam_policy_document` | Generates the JSON for the read policy |
| `aws_iam_policy` | IAM policy that allows reading this specific secret |

---

## 🔍 The Problem This Module Solves

### The WRONG way (what most beginners do):

```hcl
# ❌ WRONG — hardcoded password in tfvars:
# dev.tfvars
db_password = "MyPassword123!"

# main.tf
resource "aws_db_instance" "db" {
  password = var.db_password
}
```

**What's wrong with this?**
```
1. Password is in dev.tfvars → gets committed to Git → ANYONE who can
   read the repo knows your database password.

2. Password is in Terraform state file (terraform.tfstate) in PLAIN TEXT.
   If S3 bucket is not encrypted or misconfigured → exposed.

3. Rotating the password means editing tfvars, committing to Git,
   running terraform apply → creates a paper trail of every past password.

4. Security audit: "Show me all the places passwords are stored."
   Answer: "In 3 tfvars files, the S3 state bucket, and Git history."
   Auditor: "❌ FAIL"
```

### The RIGHT way (this module):

```
1. Password is AUTO-GENERATED by Terraform — you never see it or type it.
2. Password is stored in AWS Secrets Manager — encrypted at rest.
3. Password is NOT in any tfvars file — no Git exposure.
4. Password in state file is marked sensitive — Terraform never prints it.
5. App code retrieves password at runtime via AWS SDK — no hardcoding.
6. Rotate password: taint the random_password resource → apply → one click.
```

## 🔍 PART 1 — Random Password Generator

```hcl
resource "random_password" "rds" {
  length           = 24
  special          = true
  override_special = "!#$%&*()-_=+[]{}<>:?"

  lifecycle {
    ignore_changes = [length, special, override_special]
  }
}
```

**`resource "random_password"`** — a resource from the `hashicorp/random` provider.
It generates a random string. This is not an AWS resource — it runs locally in Terraform.

**`length = 24`** — 24 characters long.
```
A 24-character password with upper+lower+numbers+special:
Entropy ≈ 24 × log2(95) ≈ 157 bits
Time to brute-force at 1 trillion guesses/second: longer than the age of the universe.
```

**`special = true`** — include special characters (!@#$...) for extra entropy.

**`override_special = "!#$%&*()-_=+[]{}<>:?"`**
- Use ONLY these special chars, not the full set.
- Why? MySQL CLI and JDBC connection strings break on certain characters like
  `'` (single quote), `"` (double quote), `;` (semicolon), `@` (@ sign).
- We exclude those to avoid connection string parsing issues.

**`lifecycle { ignore_changes = [length, special, override_special] }`**

```
The problem without this:
  You change the length from 24 to 32 in the variable.
  Terraform detects the change.
  Terraform regenerates the password.
  RDS password is now different from what Secrets Manager has.
  App can no longer connect to the database. INCIDENT.

With ignore_changes:
  Once generated, the password NEVER changes unless you explicitly:
  terraform taint random_password.rds
  terraform apply
  → Intentional rotation, controlled process.
```

**Accessing the result:**
`random_password.rds.result` — the generated password string (sensitive value).

## 🔍 PART 2 — Secret Container (Metadata)

```hcl
resource "aws_secretsmanager_secret" "rds_password" {
  name                    = "${var.environment}/rds/master-password"
  description             = "RDS master password for ${var.environment} MySQL instance"
  recovery_window_in_days = var.recovery_window_days

  lifecycle {
    create_before_destroy = true
  }
  ...
}
```

**Think of Secrets Manager like a safe:**
- `aws_secretsmanager_secret` = the safe itself (name, location, settings)
- `aws_secretsmanager_secret_version` = the documents INSIDE the safe (the actual password)

**`name = "${var.environment}/rds/master-password"`**
- Path-style naming (using `/`) is best practice — organises secrets like a folder structure.
- e.g. `dev/rds/master-password`, `prod/rds/master-password`
- In the AWS Console they appear in a tree: `dev/` → `rds/` → `master-password`

**`recovery_window_in_days`**
```
recovery_window_in_days = 0  (dev):
  When deleted, the secret is IMMEDIATELY and permanently removed.
  terraform destroy works cleanly.
  Good for dev/test environments where secrets are recreated often.

recovery_window_in_days = 30  (prod):
  When deleted, the secret enters a "scheduled for deletion" state.
  You have 30 days to recover it if deleted accidentally.
  After 30 days: permanently gone.
  This is AWS's safety net for production secrets.
```

**`lifecycle { create_before_destroy = true }`**

```
Scenario:
  You rename the secret path from "dev/rds/password" to "dev/rds/master-password".
  Terraform must replace the secret (names are immutable).

Without create_before_destroy:
  Delete old secret → Create new secret
  During the gap: RDS module is running `depends_on` on this secret.
  If the secret doesn't exist, something might fail.

With create_before_destroy:
  Create new secret first → Update references → Delete old secret
  No gap. No risk.
```

## 🔍 PART 3 — Secret Version (The Actual Value)

```hcl
resource "aws_secretsmanager_secret_version" "rds_password" {
  secret_id = aws_secretsmanager_secret.rds_password.id

  secret_string = jsonencode({
    username = var.db_username
    password = random_password.rds.result
    engine   = "mysql"
    port     = 3306
  })

  lifecycle {
    ignore_changes = [secret_string]
  }

  depends_on = [aws_secretsmanager_secret.rds_password]
}
```

**`secret_id`** — links this version to the secret container created above.

**`secret_string = jsonencode({...})`**
- The actual password value stored in the secret.
- We store it as JSON (not just the password string) so app code can easily
  read individual fields:

```python
import boto3, json

client = boto3.client('secretsmanager', region_name='us-east-1')
response = client.get_secret_value(SecretId='dev/rds/master-password')
secret = json.loads(response['SecretString'])

host     = "dev-mysql-primary.xxxx.us-east-1.rds.amazonaws.com"
username = secret['username']   # "admin"
password = secret['password']   # "Xk9#mP2qR..." (never hardcoded!)
port     = secret['port']       # 3306
engine   = secret['engine']     # "mysql"
```

**`lifecycle { ignore_changes = [secret_string] }`**

```
Without this:
  Terraform stores the generated password in state.
  On every `terraform plan`, it compares state password to current.
  If someone manually rotated the secret in AWS Console, the values differ.
  Terraform wants to OVERWRITE the rotated password with the old one!
  Your rotation is undone. Security team is unhappy.

With ignore_changes:
  After first creation, Terraform never touches the secret value again.
  Manual rotations, Lambda-based rotations — all preserved.
```

**`depends_on = [aws_secretsmanager_secret.rds_password]`**
- The secret container must exist before we can create a version inside it.
- Terraform infers this from `secret_id` reference, but explicit is safer
  for clear student understanding.

## 🔍 PART 4 — IAM Policy for Reading the Secret

```hcl
data "aws_iam_policy_document" "read_rds_secret" {
  statement {
    sid    = "AllowReadRDSSecret"
    effect = "Allow"
    actions = [
      "secretsmanager:GetSecretValue",
      "secretsmanager:DescribeSecret"
    ]
    resources = [aws_secretsmanager_secret.rds_password.arn]
  }
}

resource "aws_iam_policy" "read_rds_secret" {
  name   = "${var.environment}-read-rds-secret-policy"
  policy = data.aws_iam_policy_document.read_rds_secret.json
}
```

**Why create an IAM policy here?**
The IAM module attaches this policy to the EC2 role.
This allows the EC2 instance to call `GetSecretValue` at runtime.

**Least privilege:**
- Only `GetSecretValue` and `DescribeSecret` — not `DeleteSecret`, `RotateSecret`, etc.
- Only on THIS specific secret ARN — not all secrets in the account.

```
resources = ["arn:aws:secretsmanager:us-east-1:123:secret:dev/rds/master-password-XXXXXX"]

vs

resources = ["arn:aws:secretsmanager:*:*:secret:*"]  ← never do this!
```

## 📤 Outputs and How They Connect

```
secrets_manager.rds_password     → rds module (db_password variable)
secrets_manager.secret_arn       → displayed after apply (for reference)
secrets_manager.secret_name      → app code uses this name to retrieve the password
secrets_manager.read_policy_arn  → iam module attaches to EC2 role
```

## ⚡ Key Concepts Used

| Concept | Where | Why |
|---------|-------|-----|
| `random_password` | password generation | Never type or store a password manually |
| `lifecycle ignore_changes` | password, secret_string | Prevent unwanted rotation undoing |
| `lifecycle create_before_destroy` | secret container | No gap during secret rename |
| `jsonencode()` | secret_string | Store structured data, not just a raw string |
| `data aws_iam_policy_document` | read policy | Structured, validated policy JSON |
| `depends_on` | secret version | Container must exist before version |
| `sensitive = true` | rds_password output | Never printed in plan/apply |
